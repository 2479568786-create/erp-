# 技术小白用 AI 开发 ERP：上手路线与避坑指南

这份指南写给“不是程序员，但想用 AI 给自己的工作做工具”的人。目标不是让你背会所有技术词，而是帮你把需求拆小、检查 AI 写出的东西、减少把错误直接带到真实店铺的机会。

## 先说清楚：这个仓库是什么、又不是什么

这是 GeekOzon ERP 的一份可供学习和继续开发的源码快照。它包括 Flask 后端、原生 JavaScript 前端、浏览器扩展，以及若干运营工作区。你可以用它研究一个小型 ERP 如何组织页面、路由、模型和服务。

但它不是一套“下载后填 API Key 就能安全运营”的商业成品：

- 当前公开仓库来自本地快照，未从服务器逐文件核实；
- 工作区索引里已注明，独立 JLC 研究前端和完整 JLC 后端不在这份快照里；
- 真实店铺凭证、AI 凭证、图片存储和运行环境需要自己配置；
- 公开源码不等于经过完整安全审计、平台合规审计或生产压力测试；
- 连接 Ozon 的写操作可能真实创建或修改商品、价格、库存和订单状态。

请把它当作学习底座和项目案例，先在本地、测试账号或单件测试商品上理解链路，再考虑接生产数据。

## 1. 下载后先认识目录，不要马上让 AI 重写

建议先看这些位置：

| 路径 | 用途 |
|---|---|
| `frontend/index.html` | 页面入口、脚本加载和布局入口 |
| `frontend/js/router.js` | 前端页面路由 |
| `frontend/js/api.js` | 前端统一 API 请求封装 |
| `frontend/js/pages/` | 各工作区的页面代码 |
| `backend/app.py` | Flask 应用创建、健康检查和整体启动入口 |
| `backend/routes/` | HTTP 路由：接收页面请求、校验参数、调用服务 |
| `backend/services/` | 业务逻辑：价格、财务、发布、图片、订单等 |
| `backend/models/` 与 `backend/schema.sql` | 数据模型和数据库结构 |
| `extension/` | 浏览器扩展源码 |
| `docs/WORKSPACE_MAP.md` | 按工作区查找前后端代码 |

一个常见请求的路径大致是：

```text
页面 frontend/js/pages/...
  → 统一请求 frontend/js/api.js
  → Flask 路由 backend/routes/...
  → 业务服务 backend/services/...
  → 数据模型/SQLite backend/models/、backend/schema.sql
  → 返回结果给页面
```

当页面“没反应”时，按这个方向逐层确认，比让 AI 一口气重写整个页面更容易定位问题。

## 2. 本地运行：先把开发环境和生产环境分开

仓库当前依赖写在 `backend/requirements.txt`。在 Windows PowerShell 中，可以按以下步骤尝试：

```powershell
cd backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python app.py
```

启动后，在浏览器打开 `http://127.0.0.1:5000/api/health`，确认后端返回健康状态。停止服务按 `Ctrl+C`。项目的 Flask 应用也提供页面入口；如果打开根地址仍无法加载页面，再检查浏览器开发者工具的 Console 和 Network，而不是先去改 API。

如果 PowerShell 不允许激活虚拟环境，可先不激活，直接运行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

不同电脑的 Python 版本、网络、系统权限会不同；遇到依赖安装问题，先记录完整错误和 Python 版本，再逐项解决。不要把 `.venv` 上传到 GitHub。

### 重要的安全提醒

- `python app.py` 会监听所有网络接口（`0.0.0.0`）；当前配置的 CORS 默认允许所有来源（`*`）。**本地学习时不要把 5000 端口开放到公网。** 如果确实要部署，先在 `backend/.env` 中限制允许的来源，并按生产环境配置 HTTPS、防火墙和认证。
- 项目启动时未配置 `SECRET_KEY` 会生成临时值；生产环境必须由部署环境提供强随机固定值，不能把它写进源码、启动脚本或公开 issue。
- 店铺的 Client-Id、Api-Key、AI 服务密钥、对象存储密钥都属于凭证。真实值只放在本地未提交的环境配置/安全凭据系统中。
- 不要把 `.env`、数据库、商品订单导出、上传图片、日志、服务器 SSH 私钥提交到公开仓库。
- 新手不要用真实店铺作为第一个测试对象。发布、改价、改库存、发货等写操作都可能造成真实业务后果。

## 3. 把一句需求拆成可验收的小任务

不要只对 AI 说：“帮我把上架做好。”这句话既没有说清入口，也没有定义成功，更没有说明哪些操作可以写 Ozon。

可以改成这样的任务说明：

```text
目标：修复采集箱里单个商品保存后刷新页面会丢失的问题。

请先只读检查，不要修改代码：
1. 找出对应页面、API 请求、后端路由和保存逻辑；
2. 说明数据现在保存在哪里，以及刷新后为什么丢失；
3. 列出最小修复方案和需要验证的文件。

我确认方案后再改。验收条件：
- 保存成功后页面显示成功提示；
- 刷新页面后仍能读到相同数据；
- 保存失败时显示可理解的错误，不伪装成成功；
- 不调用 Ozon 写接口，不改其他工作区。
```

这样的描述会迫使任务先定位根因，再限定改动范围和副作用。AI 给出修改后，再检查实际 diff；看不懂的改动不要直接部署。

## 4. 先走通一个“纵向切片”，再扩成批量功能

纵向切片就是从页面到数据库、再回到页面的一条完整小流程。以商品资料为例：

1. **页面**：输入一项资料，字段含义和单位明确；
2. **请求**：请求地址、方法、参数和返回格式明确；
3. **后端**：校验必填字段和数据类型，错误返回可读；
4. **保存**：确认数据写入正确记录，不覆盖其他店铺或 SKU；
5. **回读**：刷新页面或重新查询，能读回刚才保存的值；
6. **异常**：断网、缺字段或重复提交时，页面说明发生了什么。

先让一个商品、一家店、一个类目跑通，再扩展到批量、重试和定时任务。批量只会放大已有问题；如果单件流程不可靠，批量不会让它变可靠。

## 5. 上架接口：区分“请求成功”和“商品质量合格”

上架要拆成多个检查点，而不是只看 HTTP 请求有没有报错：

- 接口地址、认证方式、请求字段是否符合当前 Ozon 文档；
- 类目是否选对，必填属性是否完整，单位和枚举值是否正确；
- 标题、简介、主题标签是否符合目标语言与平台限制；
- 图片是否真的上传成功，返回的图片引用是否绑定到正确 SKU；
- 商品是否在 Ozon 后台出现，状态是否符合预期；
- 失败重试是否会创建重复商品或重复任务。

本项目早期的经历就是：上架接口后来能工作了，但图片上传和类目属性仍有问题，商品质量并不理想。这个案例提醒我们，**接口连通、平台接受请求、商品资料完整、最终可售，是四个不同的验收层级**。

排查 API 时，先核对请求与响应的结构，保留脱敏后的样例，再对照 Ozon 当时的官方文档。不要用真实 API Key 把请求截图发给 AI，也不要在开发日志里原样保存认证头。

## 6. 类目映射与属性：AI 翻译不能代替规则映射

类目属性问题通常不是“把中文翻成俄语”就结束了。需要考虑：

- 商品应该进入哪个 Ozon 类目；
- 目标类目的必填属性、可选属性和属性 ID 是什么；
- 属性值是自由文本、数字、单位、枚举还是多选；
- 采集到的中文值能否映射到平台允许的选项；
- 缺失或无法确定时，是否应该提示人工确认，而不是编造。

建议为一个具体类目建立小型映射表，并用几件真实但已脱敏的商品验证。把“来源字段 → 目标属性 ID → 转换规则 → 失败处理”记录下来。先覆盖最常用类目，再扩展，不要一开始追求覆盖所有 Ozon 类目。

DeepSeek 等模型可以帮助生成商品标题和描述，但输出仍需长度、语言、禁用内容和字段类型校验。模型生成“看起来合理”，并不代表平台接受或商品信息真实。

## 7. 图片：把生成、上传、绑定和验收分开

图片相关功能建议拆成独立状态：

```text
原图可读取
  → 处理/生成完成
  → 图片质量检查通过
  → 上传成功并拿到可用引用
  → 绑定到正确商品和 SKU
  → 页面重新读取后仍显示正确
```

每一步都要能看到状态、产物或错误原因。生成了本地文件，不等于 Ozon 已经能访问；上传返回成功，不等于绑定到了正确 SKU；显示“100%”也不一定代表任务成功。需要明确哪些状态是进度、哪些状态是实际完成。

若使用模板渲染，先验证一张模板、一件商品、一种文字长度和一张原图；若使用图像模型，也要对商品本体、文字和最终画面做人工复核。先解决质量标准，再批量生成。

## 8. 自动化任务：可恢复比“自动运行”更重要

一条长流水线中途失败很正常。可靠的自动化至少需要：

- 明确且可保存的步骤状态，而不是只存一个总进度；
- 每一步写入开始时间、结束时间、结果和错误摘要；
- 失败后能定位到具体步骤，并支持从安全检查点恢复；
- 对重复请求设置幂等保护，避免重复创建商品或重复扣费；
- 区分“重试失败步骤”和“从头再跑”，提示可能产生的副作用；
- 用户点击恢复后，界面要显示任务是否已排队、是否正在运行，不能只改变按钮状态。

如果任务看起来“恢复了但没跑”，建议按顺序检查：按钮是否发出请求、后端是否接受、任务状态是否变更、worker 是否在线、任务是否卡在前置校验、日志里最后一条记录是什么。不要连续点击恢复来碰运气。

## 9. AI 协作时的五个好习惯

1. **先让 AI 阅读，再让它修改。** 要求它指出文件位置、数据流和副作用。
2. **一次只做一件可验收的事。** 不要在同一个任务里同时换界面、改数据库、换 API 和改部署。
3. **要求列出将修改的文件。** 发现范围扩大时，先停下来确认原因。
4. **每次改完看 diff 并做实际测试。** 只看到 AI 说“已完成”不算验证。
5. **把“诊断”和“修复”分开。** 先得到原因和证据，再决定是否动代码；尤其是生产接口和数据修复。

可以把下面的检查清单贴给 AI：

```text
开始前：复述目标和限制；先读相关代码；列出计划修改的文件和外部副作用。
实现时：只改本任务必需部分；保留现有风格；不改无关功能。
完成后：列出 diff；说明运行了哪些测试、哪些没有运行；给出人工验收步骤；指出回滚方式。
```

## 10. 用 Git 留退路

改代码前先确认自己在哪个分支、工作区有没有别人留下的改动：

```powershell
git status --short --branch
git switch -c fix/描述问题的小分支
```

任务验证后，再看 `git diff` 和状态，只提交本次相关文件。不要用 `git reset --hard` 或随意覆盖文件来“清理”。Git 的价值不只是上传代码，更是让你知道改了什么、何时改、出问题时能回到哪个版本。

## 11. 发布到 GitHub 前的公开仓库检查

每次提交前逐项检查：

- 没有 `.env`、API Key、Client-Id/Api-Key、SSH 私钥、真实 Cookie；
- 没有数据库、订单导出、客户信息、真实商品图片或运行日志；
- 没有 `node_modules`、虚拟环境、缓存、自动备份、编译产物；
- 新增的第三方代码有可确认的许可证和版权说明；
- README 不包含真实服务器 IP、内部目录和生产账号；
- commit 作者邮箱是否会公开显示；
- `.gitignore` 是否覆盖新引入的数据文件和构建目录。

`.gitignore` 只能阻止尚未跟踪的文件被意外加入；已经提交过的密钥不会因为后来加了忽略规则而从 Git 历史消失。一旦凭证意外公开，应立即撤销/轮换凭证，并按平台流程处理仓库历史。

## 12. 建议的开发顺序

如果你也在做自己的小工具，可以按下面顺序来：

1. 记录一周里最重复、最容易出错的工作；
2. 选一个范围很小的流程，写出输入、预期结果和失败情况；
3. 先搭一个能看懂的目录和接口，不要先追求宏大的架构；
4. 用一份脱敏样例跑通页面—后端—数据库—回读；
5. 再接一个外部 API，并先从只读或低风险调用验证；
6. 对写入功能使用测试账号或单条测试数据；
7. 记录每次踩坑、根因、修复方式和验证结果；
8. 代码和文档一起维护，重要决策不要只留在聊天记录里；
9. 确认依赖许可证和数据安全后，再公开仓库。

AI 变现不一定是把软件做成产品卖给所有人。对预算有限的普通人来说，少重复操作、少犯错、把工作流程沉淀成自己的工具，也是一种很实际的回报。
