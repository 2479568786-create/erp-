# GeekOzon ERP · AI 广告监控

> 菜单位置：**促销活动 → AI广告监控**（`#/ad-monitor`）
> 数据来源：**Ozon Performance API**（`https://api-performance.ozon.ru`）

---

## 一、这个模块解决什么

业务员在 Ozon 后台**自行**开通广告（登上顶端、按点击付费、按订单付费…），
ERP 不代投、不干预投放，只做一件事：**把效果盯住，及时把人叫醒**。

它自动回答两个问题：

1. **哪些商品该处理了？** —— 已完成测评 / 点击率太低 / 花了钱没出单
2. **今天是不是花太多了？** —— 单店当日花费超线就弹窗

---

## 二、四条监控规则

| 编号 | 规则 | 默认阈值 | 含义与动作 |
|---|---|---|---|
| **R1** | 已完成测评 | 累计点击 ≥ **30** | 点击量已够，可以据此判断广告效果，标为「已完成测评」 |
| **R2** | 点击率偏低 | 曝光 ≥ **100** 且 CTR < **4%** | 曝光够了没人点 → 通常是主图/标题/定价与需求不匹配 |
| **R3** | 高花费无转化 | 花费 > **1000₽** 且 **零订单** | 钱花出去了没出单，明确的投放浪费 → 建议暂停或降价 |
| **R4** | 当日花费告警 | 单店当日 ≥ **500₽** | **弹窗**强制提醒业务员，防止预算失控 |

### 关于 R2 的「最低曝光量」
规则里额外加了「曝光 ≥ 100」的门槛。原因：不做这个限制的话，
「2 次曝光 0 次点击」会被算成 CTR 0% 并疯狂刷屏，把真正的问题商品淹没。
该门槛可在阈值设置里调整，设为 0 即恢复纯 CTR 判定。

### 三条商品规则**互相独立**，不互斥
同一商品可能同时命中多条。例如某商品已有 35 次点击（R1 达标）
但 CTR 只有 2.9%（R2 偏低）——**两件事都成立，都会各自提醒**，
不要因为「已达标」就压掉「点击率低」的告警，它们指向不同的动作。

### 阈值随时可调 —— 但**只有管理员能改**
**AI广告监控 → 阈值设置**。修改即时生效，无需重启。
CTR 阈值填百分数即可（填 `4` 或 `4.0` 都行，系统自动换算成 0.04）。

**权限规则（`PUT /api/ad-monitor/settings` 由 `@require_admin` 强制把关）**：

| 角色 | 查看阈值 | 修改阈值 |
|---|---|---|
| 管理员 admin | ✅ | ✅ |
| 业务员 salesperson | ✅（需看到自己的告警线） | ❌ 403 |
| 运营员 operator | ✅ | ❌ 403 |
| 未登录 | ❌ 401 | ❌ 401 |

**为什么业务员仍可「查看」阈值**：告警文案要说明「超出 120₽」，业务员必须知道
告警线是 500₽ 才能理解自己被警告的原因。**看得到 ≠ 管得着**——写操作一律管理员专属。

前端同样做了双重防护：非管理员看不到「阈值设置」按钮，且 `openSettings()`
内部再判一次角色（防止绕过 UI 直接调用）。

**改动留痕**：每次修改都会记录最后修改人与时间，展示在阈值弹窗顶部
（`ad_monitor_settings.updated_by_name / updated_at`），便于追溯是谁调的。

## 三、弹窗告警的触发时机

按需求「当天花费 500 卢布及以上**必须**发出警告」，采用**双重触达**：

1. **登录后立即弹** —— 订阅登录态，解析完成即检查当日花费（每个页面会话只弹一次）
2. **进入本页再提示一次** —— 页面顶部常驻红色告警条 + 弹窗

弹窗内容：店铺名、今日花费、告警线、超出金额、今日订单数，并提供「查看明细」直达页面。

## 四、必须先配置广告 API 凭证 ⚠️

**这是最容易踩的坑**：Ozon 把商品数据和广告数据拆成了**两套完全独立的 API**：

| | 商品 Seller API | 广告 Performance API |
|---|---|---|
| 地址 | `api-seller.ozon.ru` | `api-performance.ozon.ru` |
| 认证 | Client-Id + Api-Key（请求头） | OAuth2 → Bearer Token |
| 凭证 | 「店铺管理」里已填 | **需要另外申请** |

**两套凭证不通用。** 只用商品 API Key 是拉不到广告数据的。

### 申请步骤
1. 打开 `seller.ozon.ru/app/settings/api-keys`
2. 切到 **Performance API** 标签页
3. 创建/选择服务账号 → **Добавить новый ключ**
4. 拿到 `client_id`（形如 `xxx@advertising.performance.ozon.ru`）和 `client_secret`

### 填入 ERP
**AI广告监控 → 授权状态 → 「填写凭证」**（仅管理员）。
保存时会**立即向 Ozon 验签**并把活动数回报，填错当场就能发现。
密钥加密入库，接口不会回传明文。

> Token 有效期 1800 秒，系统自动缓存并在过期前 5 分钟续签，无需人工干预。

## 四补、实测踩坑记录（对接时真实遇到，务必别踩回去）

Ozon 的文档和真实返回**有出入**，以下都是实测确认过的：

| # | 现象 | 后果 | 处理 |
|---|---|---|---|
| 1 | `placement` 返回的是**数组** `['PLACEMENT_SEARCH_AND_CATEGORY']` | 直接存进 SQLite 报 **Error binding parameter 5 - probably unsupported type**，同步直接失败 | 用 `/` 拼成字符串再存 |
| 2 | 付费方式的键是 **`PaymentType`**（首字母大写），不是文档写的 `paymentType` | 按小写取值永远拿到空串，前端「付费方式」列一片空白 | 两种写法都兼容 |
| 3 | `POST /statistics/products/sku` 只接受**今天或昨天** | 传 30 天直接 400：`date range must contain only today or yesterday`，`30 天累计点击` 算不出来 | 改用异步报表（支持 62 天、逐日逐 SKU） |
| 4 | 报表下载返回的是 **ZIP**（多活动）或裸 CSV（单活动） | 按文本 decode 会破坏 ZIP → `BadZipFile` | 必须走**二进制**下载 |
| 5 | 报表 CSV 是**分号分隔 + 俄文表头 + 俄式数字**（`1 234,56`） | 按逗号切列会全乱 | 按俄文表头归一化映射字段 |
| 6 | CSV 末尾有 `Всего`（合计）行，且与 `Продано товаров` / `Продано товаров модели` 等近似列名并存 | 误取会算错 | 跳过合计行；表头归一化后精确匹配 |
| 7 | 报表生成接口有**频率限制** | 短时间内反复提交会 429：`limit of reports reached` | 同步不要高频点；等配额恢复 |

### 数据源结论
商品级指标（R1/R2/R3）**以异步报表为唯一数据源**：
`POST /api/client/statistics` → 轮询 `state=OK` → `GET /api/client/statistics/report`（二进制）。
它一次能给 **62 天**、且逐行返回「日期 + SKU + 商品名 + 曝光 + 点击 + CTR + 花费 + 订单 + 销售额」，
正好覆盖三条规则的全部字段。

按天落库到 `ad_sku_stats`（`UNIQUE(store_pk, sku, campaign_id, stat_date)`），
规则评估时自行 SUM 出「近 30 天」的口径——快速接口给不了长区间，只能这样累计。

## 四补2、已知范围限制

- **「按订单付费」(CPO) 目前只同步活动本身，不做商品级效果判定。**
  原因：CPO 的在推商品接口 `/campaign/search_promo/v2/products` 只返回
  `views`（本周/上周）与出价，**没有花费/点击/订单**；
  它是「按成交订单抽佣」的计费模型，与 CPC 的「30 次点击 / CTR 4% / 花费超 1000」不是一回事。
  要覆盖 CPO 的成交明细，需要再接 `/statistic/products/generate` 报表（本次对接时该接口触发限流，未验证）。
- **CPC 的四条规则不适用于 CPO**：CPO 没成交就不扣费，因此「花了钱没出单」这条对它无意义。

## 五、数据口径

- **时区**：一律按**莫斯科时间（MSK, UTC+3）**结算自然日，与 Ozon 报表一致。
  页面上标注的「今日」就是 MSK 的今天，不是服务器本地时间。
- **商品聚合**：一个商品可能同时投多个活动，指标按「店铺 + SKU」合并计算。
  CTR 不跨活动相加，而是用 **总点击 / 总曝光** 重算，避免加权错误。
- **同步窗口**：商品指标取近 **30** 天，日花费取近 **14** 天（可改）。
- **数据刷新**：点击「同步广告数据」拉取。单店失败不影响其它店铺，
  失败原因写入同步日志并显示在「授权状态」卡片上。

## 六、接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ad-monitor/overview` | 看板：配置状态 + 当日花费 + 三档告警 |
| GET | `/api/ad-monitor/alerts` | 告警集合（弹窗数据源） |
| GET | `/api/ad-monitor/products?type=` | 商品告警，type = test_complete / low_ctr / no_conversion |
| GET | `/api/ad-monitor/campaigns` | 广告活动列表 |
| GET | `/api/ad-monitor/sync-logs` | 同步日志 |
| POST | `/api/ad-monitor/sync` | 触发同步（可传 `{storePk}` 只同步某店） |
| GET/PUT | `/api/ad-monitor/settings` | 读取 / 修改阈值（PUT 仅管理员） |
| POST | `/api/ad-monitor/stores/<pk>/credentials` | 保存凭证并验签（管理员） |
| POST | `/api/ad-monitor/stores/<pk>/test` | 连接自检（管理员） |

**权限**：业务员只能看到自己名下店铺，可查看与手动同步，不能改阈值/凭证；
管理员可看全部、可同步、可改配置。与其它模块的角色模型一致。

## 七、数据表

| 表 | 用途 |
|---|---|
| `ad_campaigns` | 广告活动（付费方式/展示位置/状态/预算） |
| `ad_sku_stats` | 商品级指标（R1/R2/R3 数据源） |
| `ad_daily_stats` | 每日花费（R4 数据源） |
| `ad_sync_log` | 同步日志（排障用） |
| `ad_monitor_settings` | 阈值配置（单行表） |

`stores` 表新增：`perf_client_id` / `perf_client_secret`（加密）/
`perf_token` / `perf_token_expires_at` / `ad_monitor_enabled`。

## 八、排障

| 现象 | 原因与处理 |
|---|---|
| 页面提示「未配置凭证」 | 正常，去「授权状态」填 Performance API 凭证 |
| 凭证保存后提示验证失败 | `client_id`/`client_secret` 不对，或该账号没有广告权限 |
| 同步成功但无数据 | 该店在 Ozon 侧确实没有跑广告；或广告刚开、还没产生统计数据 |
| 数据看起来是昨天的 | Ozon 报表有结算延迟，MSK 当天的数据当天可能不完整 |
| 弹窗没出现 | 当日花费未达告警线；或已是本页面会话的第二次加载（只弹一次） |
