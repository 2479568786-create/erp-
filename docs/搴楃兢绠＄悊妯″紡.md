# GeekOzon ERP · 店群管理模式

> 适用规模：**5~7 人小团队**（1 名店群负责人 + 5~6 名业务员），每人负责多家 Ozon 店铺。
> 本文说明账号角色、店铺绑定机制、接口与界面入口、以及日常运转方式。

---

## 一、核心设计：一个管理员持有店铺，按人分配

小团队做店群的关键矛盾是：**店铺授权（Client-Id / Api-Key）必须集中管控，但日常运营必须下放到人。**
本模式的处理方式是——店铺始终挂在系统里（授权只有管理员能改），
再通过「归属」字段把**数据可见性**分配给业务员：

```
Ozon 店铺（授权集中）
      │  stores.account_id
      ├── NULL      → 公共店铺：仅管理员可见（尚未分配）
      ├── 业务员甲   → 甲登录后可见该店商品/订单/财务
      └── 业务员乙   → 乙登录后可见该店商品/订单/财务
```

**一家店铺同一时刻只属于一个人**（1:N，不是多对多）。这样业绩、利润、退货损失
都能干净地归到具体的人头上，不会出现「两家店都算我做的」这类扯皮。

## 二、角色模型

| 角色 | 代码 | 可见范围 | 能做什么 |
|---|---|---|---|
| 管理员 | `admin` | **全部店铺**（不受绑定影响） | 店铺授权、账号管理、店铺分配、全部数据 |
| 业务员 | `salesperson` | **仅本人名下店铺**，未分配=不可见 | 采集、上架、订单、财务（受限）、填业绩 |
| 运营员 | `operator` | 同业务员（按受限处理） | 同业务员，用于不归属具体的运营岗 |

> 说明：`operator` 是兼容角色，权限与业务员一致。管理员天然可见全部店铺，
> 因此**不能**把店铺绑定给管理员账号（后端会拒绝并给出明确提示）。

可见性在后端强制生效，前端传的 `accountId` 越权参数会被忽略：

- `utils/auth.py::visible_store_pks() / visible_ozon_store_ids()`
- `routes/store_routes.py`、`order_routes.py`、`online_product_routes.py`、`product_routes.py`、
  `dashboard_routes.py`、`dashboard_control_routes.py` 均调用上述过滤。

## 三、界面入口

**系统设置 → 用户管理**（菜单项 `data-admin-only`，非管理员自动隐藏）

页面为「用户管理 · 店群」，分四个页签：

| 页签 | 用途 |
|---|---|
| **成员与绑定** | 账号列表（角色/状态/**名下店铺数**/涉及分组/最近登录）+ 分配、编辑、删除、重置密码 |
| **未分配店铺** | 列出公共店铺，勾选后一键分配给某人 |
| **分组分布** | 按店铺分组展示「已绑定 / 未分配」占比，支持**整组分配**、**整组解绑** |
| **变更日志** | 绑定/解绑/转移的完整审计轨迹 |

顶部看板：店铺总数、已绑定、未分配（公共）、团队成员、店铺分组数。

> 旧入口（店铺管理页右上角「用户管理」按钮）已改为跳转到本页，历史弹窗保留并加了跳转入口。

## 四、绑定接口

所有接口均为**管理员专属**（`require_admin`），统一前缀 `/api`。

### 4.1 店群总览

```http
GET /api/store-assignment/overview
```
一次返回看板所需的全部数据，避免前端多次往返：

```json
{
  "totals":   { "stores": 12, "bound": 9, "unassigned": 3, "members": 6, "activeMembers": 6, "groups": 3 },
  "members":  [ { "id": 2, "username": "sales_a", "storeCount": 3, "groups": ["A组"],
                  "stores": [ { "id": 1, "storeId": "216800183", "alias": "店铺A", "group": "A组" } ] } ],
  "unassigned": [ { "id": 7, "storeId": "216800199", "alias": "新店", "group": "默认" } ],
  "groups":   [ { "name": "A组", "storeCount": 4, "boundCount": 4, "unboundCount": 0, "ownerNames": ["业务员甲"] } ]
}
```

### 4.2 可分配成员 / 某人名下店铺

```http
GET /api/store-assignment/members        # 非管理员账号 + 各自店铺数
GET /api/users/<uid>/stores              # 某成员名下的店铺明细
```

### 4.3 批量绑定（核心接口）

```http
POST /api/store-assignment/bind
Content-Type: application/json

{
  "accountId": 2,
  "storePks": [1, 2, 3],
  "mode": "add",
  "remark": "新人接手"
}
```

**目标店铺的四种定位方式**（可组合，结果自动去重）：

| 字段 | 含义 |
|---|---|
| `storePks: [...]` | 按 `stores.id` 主键 |
| `storeIds: [...]` | 按 Ozon 店铺 ID |
| `group: "A组"` | 该分组下**全部**店铺 |
| `all: true` | 全部店铺 |

**两种分配模式**：

| mode | 语义 | 适用场景 |
|---|---|---|
| `add`（默认） | 把勾选店铺**追加**到该业务员名下；已被他人持有的店铺会**转移**过来 | 新人入职、加店 |
| `replace` | 该业务员名下店铺**以本次勾选为准**，未勾选的现有店铺自动解绑为公共店铺 | **人员交接 / 离职交接** |

**返回体**区分了四种结果，前端据此给出准确提示：

```json
{
  "counts": { "bound": 2, "transferred": 1, "skipped": 0, "released": 0 },
  "bound":       [ /* 本次新绑定 */ ],
  "transferred": [ { "alias": "店铺B", "fromName": "sales_b" } ],
  "skipped":     [ /* 本就属于该业务员，幂等跳过 */ ],
  "released":    [ /* replace 模式下被释放 */ ]
}
```

> 幂等性：把已经属于某人的店铺再分配给他，不会报错也不会重复写日志，计入 `skipped`。

### 4.4 批量解绑

```http
POST /api/store-assignment/unbind
{ "storePks": [1,2], "accountId": 2 }
```
定位方式同 `bind`。可选的 `accountId` 用于**限定只解绑该业务员名下的店铺**，防止误伤他人店铺。
解绑后店铺回到「公共店铺」状态（仅管理员可见），**店铺本身与授权信息不会被删除**。

### 4.5 变更日志

```http
GET /api/store-assignment/logs?limit=50&storePk=3
```
记录每次变更的：时间、动作（绑定/解绑/转移）、店铺、**归属变更（从谁 → 到谁）**、操作人、备注。

### 4.6 兼容接口

原有的单店绑定接口继续可用，与本模块**共用同一份数据真相**（`stores.account_id`），可混用：

```http
PUT /api/stores/owner    { "storePk": 1, "accountId": 3 }   # accountId=null 即解绑
```

## 五、数据库

### `stores.account_id`

```sql
account_id  INTEGER,   -- NULL = 公共店铺；否则 = 所属账号
FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE CASCADE
```
索引：`idx_stores_account_id`

> 注意：`stores.account_id` 的外键带有 `ON DELETE CASCADE`，但 `Account.delete()`
> 会**先**把名下店铺 `account_id` 置空再删账号，因此删人不会连带删店。

### `store_binding_log`（审计表）

```sql
CREATE TABLE store_binding_log (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    store_pk        INTEGER NOT NULL,
    store_id        TEXT    NOT NULL DEFAULT '',   -- 冗余快照，店铺删除后仍可追溯
    store_alias     TEXT    NOT NULL DEFAULT '',
    action          TEXT    NOT NULL CHECK(action IN ('bind','unbind','transfer')),
    from_account_id INTEGER,                       -- NULL = 公共
    to_account_id   INTEGER,                       -- NULL = 解绑为公共
    operator_id     INTEGER,
    operator_name   TEXT    NOT NULL DEFAULT '',   -- 名称快照
    remark          TEXT    NOT NULL DEFAULT '',
    created_at      TEXT    NOT NULL DEFAULT (datetime('now'))
);
```
表定义同时写在 `backend/schema.sql`，并在路由模块内惰性建表（兼容任意加载顺序）。

## 六、首次部署

```bash
cd backend
python -m pip install -r requirements.txt

# 1) 创建第一个管理员（仅当没有 admin 时才允许）
python scripts/bootstrap_admin.py admin <你的密码> <昵称>
#    查看现有账号：python scripts/bootstrap_admin.py --list

# 2) 启动服务（前端由 Flask 一体化托管）
python app.py            # http://127.0.0.1:5000
```

随后：**登录 → 店铺管理 → 添加店铺（填 Ozon Client-Id / Api-Key）→ 系统设置 → 用户管理 → 新建业务员 → 分配店铺**。

## 七、5~7 人团队的日常运转建议

1. **建组再建人**：先在「店铺管理」里用分组把店铺按品类/国家/负责人倾向分好
   （如「3C 组」「家居组」「新店组」），分配时用**整组分配**比逐店勾选快得多。
2. **一人一组**：让每个业务员对应一个或少数几个分组，避免交叉持有。
   分组页签能直接看出「这个组还有几家没分配」。
3. **离职交接走 `replace`**：把人名下的店铺**覆盖式**交给接手人，
   未勾选的店铺会自动释放，不会遗留孤儿店铺。
4. **公共店铺要清零**：未分配看板的数字应长期为 0。
   非 0 意味着有人开了新店但没分配——新店对业务员不可见，容易被遗忘。
5. **用备注留下原因**：交接、临时支援等操作在备注里写清楚，变更日志就是团队的操作留痕。
6. **禁用而非删除**：员工暂时离岗用「禁用」（登录被拒但归属与历史保留）；
   确认永久离职再删除账号（店铺自动回退为公共店铺）。
7. **定期核对**：财务中心的业绩榜按 `PublishRecord.publisher` 归集，
   退货损失按登记人归集；如果某人店铺数变了，记得同步核对业绩口径。

## 八、权限与安全要点

- **绑定接口全部管理员专属**：业务员调用 `/api/store-assignment/*` 与 `/api/users/*` 一律 403。
- **无法绑定给管理员**：`accountId` 指向 admin 会被直接拒绝。
- **已禁用账号不可被分配**：避免把店铺挂到登不进去的账号上。
- **越权参数被忽略**：业务员请求列表类接口时，传入的 `accountId`/`store_id` 会被角色强制覆盖。
- **店铺密钥不外泄**：`/api/stores` 返回的 `apiKey` 恒为 `******`，只回传 `hasApiKey`。
- **解绑不删店**：解绑只清空归属，授权与历史数据保留。

## 十、当前限制与后续可扩展方向

- **单店单归属**：不支持一家店同时挂给两人。若需「主负责人 + 协作者」，
  需新增 `store_collaborators` 关联表并改造 `visible_store_pks()`。
- **审计表只记绑定动作**：不记录账号本身的增删改。
- **无分配配额校验**：可以给一个人分配任意多店铺，暂不做上限提醒。
- **`data/category_mapping_general.py`**：该文件在归档时缺失，已按调用方契约重建为
  **兼容层**（颜色词典/品牌型号默认值可用，`GENERAL_MAPPINGS` 与 `CATEGORY_GROUPS` 留空，
  因为 Ozon 类目 ID 必须真实，凭空编造会导致上架到错误类目）。
  恢复方式见该文件头部说明（放 JSON 文件或从类目管理页导出候选）。
