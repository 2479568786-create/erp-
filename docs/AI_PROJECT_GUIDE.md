# 把 GeekOzon ERP 交给 AI：阅读指南

这份文档帮助非程序员把仓库交给 AI 阅读、解释或协助修改。目标是让 AI 基于真实代码讲清楚，不要因为页面名称或注释就想当然地认定功能已经完成。

## 建议 AI 按这个顺序读

1. [`README.md`](../README.md)：项目用途、范围和启动入口。
2. [`docs/WORKSPACE_MAP.md`](WORKSPACE_MAP.md)：按运营工作区快速定位文件。
3. [`backend/app.py`](../backend/app.py) 与 [`backend/routes/__init__.py`](../backend/routes/__init__.py)：应用创建、前端托管、鉴权和路由注册。
4. [`frontend/index.html`](../frontend/index.html)、[`frontend/js/app.js`](../frontend/js/app.js)、[`frontend/js/router.js`](../frontend/js/router.js)：页面如何加载和切换。
5. 对应页面、API、路由、服务、模型与测试：沿一条具体功能链路核对，不要仅凭文件名下结论。

## 项目结构：用简单的话理解

| 位置 | 可以把它理解成 | 常见问题 |
|---|---|---|
| `frontend/js/pages/` | 每个工作区的页面和交互 | 页面显示什么、按钮触发什么请求？ |
| `frontend/js/api.js` | 前端调用后端的公共入口 | 请求发往哪里、失败如何处理？ |
| `frontend/js/router.js`、`app.js` | 页面注册、切换和启动 | 菜单点进去加载哪个页面？ |
| `backend/routes/` | 后端的 HTTP 入口 | 参数如何读取、校验和返回？ |
| `backend/services/` | 实际业务处理 | 数据怎样转换、调用平台或保存？ |
| `backend/models/`、`backend/schema.sql`、`backend/db.py` | 数据表与数据库访问 | 数据存在哪里、如何关联店铺/SKU？ |
| `backend/tests/` | 自动化测试样例 | 哪些行为已有测试覆盖？ |
| `extension/` | 浏览器扩展 | 如何读取网页并把数据送入 ERP？ |
| `docs/` | 工作区索引和项目说明 | 哪些模块已知、有哪些缺失和历史背景？ |

典型的数据流如下；具体功能可能不同，必须沿代码验证：

```text
用户操作
  → frontend/js/pages/ 中的工作区页面
  → frontend/js/api.js 中的请求方法
  → backend/routes/ 中的 Flask 路由
  → backend/services/ 中的业务逻辑
  → backend/models/ 或数据库
  → 结果返回页面并刷新显示
```

如果流程还会调用 Ozon 或第三方 AI，外部请求通常位于服务层附近。应继续核对请求字段、认证方式、响应解析、错误分支和是否有副作用。

## 先分清“看起来有”与“确实完成”

仓库中存在某个页面、按钮、路由或服务，只能说明代码里有相应实现痕迹，不能单独证明线上可用。请让 AI 分别说明：

- **静态发现**：从哪些文件、函数或测试看到了什么；
- **代码推断**：按代码路径推测会发生什么；
- **实际验证**：具体运行了哪些测试或本地步骤；
- **未知/未覆盖**：需要凭证、线上环境或真实 Ozon 店铺才能确认的部分。

特别要区分 API 请求被发送、平台接受请求、商品资料完整、商品最终可售。也要区分图片生成、文件保存、上传、SKU 绑定和页面重新读取。

## 已知边界和容易误读的地方

- 这份仓库来自 2026-09-06 本地快照，不保证与服务器当前部署版本一致。
- 独立 JLC 研究工作台及其完整后端不在本仓库；`jlc_pricing_service.py` 只代表 JLC 相关定价代码。
- 目录中有 AI、上架、图片、财务等模块，但配置、凭证、平台规则和外部服务状态决定实际能否运行。
- 运行测试不等于已对 Ozon 线上商品做过端到端验证；没有凭证的情况下应明确写“未验证”。
- 不要从数据库、环境文件或日志中输出实际密钥、Cookie、店铺凭证和客户/订单数据。

## 给 AI 的可复制任务模板

```text
我是技术初学者，请先用通俗中文复述你对目标的理解。

目标：<写一个具体问题或改动>
我看到的现象：<错误提示、页面行为或截图描述>
期望结果：<怎么判断它已解决>
限制：先只读诊断 / 可以修改代码；不要调用真实 Ozon 写接口；不要改其他工作区。

请先不要直接修改。先：
1. 按“前端页面 → API → 后端路由 → 服务 → 数据库/外部平台”追踪相关链路；
2. 列出证据文件和关键函数；
3. 区分已经确认的事实、基于代码的推断和仍未知的部分；
4. 给出最小方案、涉及文件、风险和验证方法。

我确认后再实施。完成后请给我：改了什么、测试结果、未验证的部分，以及我该如何手动验收。
```

如果用户已经明确要求直接修改，可以直接开始，但仍应先检查相关链路、工作区状态和外部副作用。

## 需要新增功能时的排查顺序

1. 用 `rg` 搜索页面名、按钮文字、API 路径或字段名。
2. 从前端页面找到实际请求函数；不要只根据菜单标题判断。
3. 在 `backend/routes/` 找到接收请求的路由，核对方法、参数和权限。
4. 继续追到 `backend/services/`，找数据转换、数据库操作和外部 API 调用。
5. 查看相关模型、表结构与 `backend/tests/` 中的测试。
6. 修改最少的必要文件；运行相关测试并查看完整 diff。
7. 报告实际验证过的范围；没有线上条件就不要说“线上已修复”。

## 给读者的提醒

AI 可以帮助你读目录、解释函数、总结数据流和提出验证步骤，但它也可能误读旧代码或编造不存在的接口。遇到不确定结果，要求它提供文件路径、函数名和证据；在真实店铺操作、删除数据、改价、发货或部署前，先人工复核。
